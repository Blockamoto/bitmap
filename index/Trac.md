# Trac District Indexer Audit

**Audit date:** 22 October 2026  
**Status:** In progress; reviewed one rule at a time  
**Scope:** Bitmap **District** inscription eligibility and winner selection only. Excludes Parcel, ownership, transfers, tapping, and staking.  
**Purpose:** Document the District rules actually implemented by Trac-related indexers, the evidence for each rule, and how the implementation changed over time. Extract candidate rules for the separate District Rule Registry. **This page is evidence, not itself a canonical Bitmap ruleset or a change to the registry.**

## Source identity and historical limitations

Trac has more than one relevant historical public artifact. Do **not** treat the later Rust implementation as proof of what the original 2023 production service enforced.

1. [BennyTheDev/trac-bitmap-public-endpoint](https://github.com/BennyTheDev/trac-bitmap-public-endpoint), created 20 July 2023. Public repository history and its README document Bitmap API access. The repository's current tree contains **README.md only**; no District validation/writer implementation is published there. It is evidence that public lookup functionality was described in 2023, **not** code evidence for a MIME or eligibility rule.
2. [Trac-Systems/ord-tap](https://github.com/Trac-Systems/ord-tap), a later published Rust implementation. Its first public commit is [`3f3f851`, 19 September 2025](https://github.com/Trac-Systems/ord-tap/commit/3f3f851a00301b780e333fc9d8a3c3eaf29920e3), with no parent in that repository. Its later changes can establish **implementation history from that initial public snapshot onward**, but cannot by themselves establish when a rule first appeared in Trac's original service.
3. Prior investigation is preserved in [the District-only Trac audit](../ruleset/District%20Rule%20Registry/TRAC-DISTRICT-AUDIT.md). This indexer page draws on that investigation while keeping the ruleset registry separate.

**Evidence convention:** For every extracted rule, record (a) exact code behaviour, (b) earliest *verified* version, (c) subsequent changes with commit links, (d) any earlier history not established, and (e) whether the rule is proposed for the registry, already represented there, or still unresolved. Distinguish a source commit's date from the actual historical date of introduction.

**Next evidence path:** Locate a dated original writer repository, distribution/package, source archive, or direct confirmation from Trac/BennyTheDev; alternatively compare independently archived 2023 API outputs against competing District inscriptions. Keep authored specifications, public lookup descriptions, and observed indexing/validation behaviour in distinct evidence categories.

## TAP / ord-tap succession: source-lineage checkpoint (22 October 2026)

**Question:** Did TAP / `ord-tap` succeed the original Trac Bitmap writer, and does its public history expose the missing 2023 District eligibility code?

- **8 August 2023, separate TAP-facing API:** [`BennyTheDev/trac-tap-public-endpoint`](https://github.com/BennyTheDev/trac-tap-public-endpoint) was created and documents token-query access through Trac. Its published repository contains **README.md only**, not an index writer. Its published endpoints did not include the later `getBitmap` lookup. An example token with ticker `bitmap` is **not evidence of a District lookup**.
- **15–25 January 2024, TAP network reader:** [`Trac-Systems/tap-reader`](https://github.com/Trac-Systems/tap-reader) is a public NodeJS/Hyperbee-Holepunch reader. The [25 January 2024 README snapshot](https://github.com/Trac-Systems/tap-reader/blob/6e26396596dafdc3025c2fbf5cf24eb429f1e20e/README.md) explicitly says the **indexers/writers supplying data on the channel were not part of the public Trac Core release yet**. A reader queries distributed data; its existence does not publish the logic deciding winning District claims.
- **10 September 2024, first verified public TAP reader Bitmap API integration:** [commit `2800187`](https://github.com/Trac-Systems/tap-reader/commit/2800187210160ff9d504985f2d9c869eb3c65aec) is titled *integrated Bitmap API* and adds `getBitmap`, `getBitmapByInscription`, historical wallet and Bitmap event readers (plus related DMT routes). The January 2024 reader README does not expose those Bitmap getters. These additions establish **read-side integration by September 2024**, not the implementation or exact start date of underlying writer validation.
- **19 September 2025, standalone public Rust validator:** [`Trac-Systems/ord-tap`](https://github.com/Trac-Systems/ord-tap) describes itself as an `ord` modification and a **standalone port of a peer-to-peer indexer and validator based on Trac Network**, with Bitmap indexing. Its initial [public commit `3f3f851`](https://github.com/Trac-Systems/ord-tap/commit/3f3f851a00301b780e333fc9d8a3c3eaf29920e3) is evidence for the Rust port from that snapshot forward, **not** proof that the original 2023 writer used identical logic.
- **30 May 2026, writer transport mirror:** [`Trac-Systems/tap-writer-ordtap`](https://github.com/Trac-Systems/tap-writer-ordtap) mirrors `ord-tap` state into a classic TAP Hyperbee feed consumed by `tap-reader`. It is a **new compatibility publisher**, not the missing original 2023 writer.

**Historical replay boundary, not publication date:** The initial [19 September 2025 `ord-tap` Rust snapshot](https://github.com/Trac-Systems/ord-tap/blob/3f3f851a00301b780e333fc9d8a3c3eaf29920e3/src/index/updater/inscription_updater/tap/mod.rs#L9-L11) sets `TAP_BITMAP_START_HEIGHT = 779_832` (Bitcoin mainnet block **779,832**, mined **8 March 2023**), while the broader `TAP_START_HEIGHT = 801_993` begins **6 August 2023**. [Block-date chronology for 779,832](https://blockspace.wiki/timeline/); [block 801,993 date](https://hashxp.org/en/bitcoin/blocks/801993/transactions/5cb6bb8a1179897172fd1169fe87662ccf31d9162b40c34660729e446c94a891). This configures how far back a current node can **replay historic Bitcoin blocks** for Bitmap processing; it does **not** show that Bitmap claims, TAP's public implementation, or the same rule checks already existed on 8 March 2023. Do not conflate replayed chain coverage with public writer availability or original service behaviour.

### Main Settlement Bus (MSB): Trac Network transaction settlement, not an identified Bitmap District writer (checked 22 October 2026)

- **Identity and date:** [`Trac-Systems/main_settlement_bus`](https://github.com/Trac-Systems/main_settlement_bus), published as the `trac-msb` JavaScript package, was created on **21 February 2025** (GitHub repository creation metadata and [initial commits](https://github.com/Trac-Systems/main_settlement_bus/commits/main/)). Its [README](https://github.com/Trac-Systems/main_settlement_bus/blob/main/README.md) describes a peer-to-peer transaction validator and append network using Pear/Holepunch. This does **not** identify an older 2023 District writer.
- **Actual function:** [MSB core entrypoint](https://github.com/Trac-Systems/main_settlement_bus/blob/main/src/index.js) constructs replicated network/state, validates/broadcasts transfers and transactions, and exposes confirmed/unconfirmed transaction and account balance lookups. [MSB HTTP API](https://github.com/Trac-Systems/main_settlement_bus/blob/main/docs/trac_network_http_api.openapi.yaml) deals with Trac addresses (`trac1...`), balances, fees and transaction records. [Trac Network's architecture documentation](https://docs.trac.network/documentation/trac-network/decentralization) distinguishes the MSB's transaction settlement from individual app/contract execution. In this context `mainnet` means **Trac Network mainnet**, not a Bitcoin-block ingestion mode.
- **District source relevance:** The checked current default-branch code searches for `bitmap`, `inscription` and `bitcoin` produced no relevant files, and the inspected `src/index.js` validates Trac-network transaction payloads rather than `<height>.bitmap` inscription bodies. The MSB has roles called *indexer*/*writer*, but those names refer to its own replicated Trac ledger and do **not** establish Bitcoin Ordinals District indexing. **Conclusion: related Trac infrastructure, but not evidence for the missing 2023 Bitmap claim validator.** This is a repository-level finding, not a proof that no private or older component shares architecture.
- **No registry action:** Do not extract District validity/winner rules from the MSB or conflate the two independent meanings of *validator* and *indexer*.

**Direct code-path confirmation (reader versus indexer):** In [`tap-reader` at the September 2024 Bitmap-integration commit](https://github.com/Trac-Systems/tap-reader/blob/2800187210160ff9d504985f2d9c869eb3c65aec/src/TapProtocol.mjs#L1167-L1188), `getBitmap` reads the existing `bm/<block>` key from its Hyperbee state and `getBitmapByInscription` follows `bmh/<id>` to the stored claim record. The reader is **not shown parsing or validating District inscriptions** in those methods. Conversely, [`ord-tap`'s initial Rust `index_bitmap_created` implementation](https://github.com/Trac-Systems/ord-tap/blob/3f3f851a00301b780e333fc9d8a3c3eaf29920e3/src/index/updater/inscription_updater/tap/ops/bitmap.rs#L4-L51) **does** parse the inscription body, check its target height and existing winning `bm/<block>` record, and write a new Bitmap record. Therefore, `ord-tap` **really is a District indexer**, while `tap-reader` is a querying/replication layer on top of index output. The September 2024 reader interface **does not by itself identify or date the writer's actual implementation**, nor establish any 2023 writer rule.

**Conclusion and audit boundary:** TAP is a plausible technological successor to Trac's early centralized Bitmap-facing services; `ord-tap` is a demonstrable later standalone successor to the Trac-network writer. The **2023–2025 writer implementation remains unlocated** in the checked public repositories. Do not treat read-side endpoints, protocol specifications, Rust backported historical activation heights, and actual 2023 writer behaviour as interchangeable evidence. Audit only District rules here. No registry additions follow merely from these lineage findings.

## Rule-by-rule audit

### TRAC-D01 — Text MIME family exception

**Implementation behaviour:**
- At the initial public Rust snapshot (19 September 2025), the intake guard accepted a declared content type if the byte/string representation began with `text/` **or** `application/json`. This is a string-prefix test, not a parsed MIME family test. District candidates still had to pass the separate body and block-height checks.
- The [25 September 2025 commit `acf6b7b`](https://github.com/Trac-Systems/ord-tap/commit/acf6b7bbc7862e50999edd42c02ae170dfe23eea) narrowed the text branch to `starts_with("text/plain")` while keeping `application/json` as an alternative prefix. A malformed value such as `text/plainbogus` could match the latter text prefix; this is not the same as a standards-compliant media-type parser.

**Dated evidence:**
- **19 Sep 2025, earliest verified public code:** [initial Rust commit `3f3f851`](https://github.com/Trac-Systems/ord-tap/commit/3f3f851a00301b780e333fc9d8a3c3eaf29920e3) and [the intake source at that commit](https://github.com/Trac-Systems/ord-tap/blob/3f3f851a00301b780e333fc9d8a3c3eaf29920e3/src/index/updater/inscription_updater.rs#L984-L989) show `ct.starts_with("text/") || ct.starts_with("application/json")`.
- **25 Sep 2025, verified narrowing:** [commit `acf6b7b`](https://github.com/Trac-Systems/ord-tap/commit/acf6b7bbc7862e50999edd42c02ae170dfe23eea) explicitly replaces the `text/` test with `text/plain`. This commit also changed delegated-content resolution; that is a **separate rule** to audit later.
- **Before 19 Sep 2025:** The 2023 public API repository does not expose the original District writer or its MIME check. **Earliest public code observed is not proof of first introduction or 2023 production behaviour.**

**Extracted candidate registry rule:** *Text MIME Family Exception*, proposed default `0` (off). When enabled, allow otherwise valid canonical District claims with MIME labels beginning `text/`, rather than requiring only `text/plain`; exact prefix-matching versus parsed MIME semantics is an additional audit distinction. This is an alternative to the narrower baseline text MIME rule, not permission for arbitrary non-District bodies.

**Registry status:** Candidate already documented as [Text MIME family exception](../ruleset/District%20Rule%20Registry/text-mime-family-exception.md); **no registry edits or numbering made by this page**.

**Open history checks:** Find independently dated pre-September-2025 Trac writer, archived source, deployment evidence, or test fixtures that establish whether `text/*` was accepted earlier. In their absence, keep the historical introduction **unknown**. Literal MIME-prefix behaviour is now registered as a [separate provisional compatibility option](../ruleset/District%20Rule%20Registry/mime-string-prefix-compatibility.md); whether it changes actual historical winners still requires tests.

### TRAC-D02 — JSON MIME exception

**Implementation behaviour:**
- The District intake gate accepts a content-type **string beginning with** `application/json`, even though the candidate's content must still pass the exact canonical `<height>.bitmap` parser. A body such as `840000.bitmap` with a JSON MIME label can pass this gate; a JSON object such as `{"height":840000}` does **not** pass the District body parser.
- This is a literal string-prefix test, **not** a parsed MIME type equality check. Literal `application/json` prefix matching is recorded as a [separate provisional compatibility option](../ruleset/District%20Rule%20Registry/mime-string-prefix-compatibility.md); whether any real District outcome depends on it remains open.
- The initial Rust snapshot applies the MIME guard to the original payload. From the 25 September 2025 delegation change, it applies the guard to the *effective* payload after single-level delegate resolution. Delegation acceptance and resolution will be audited as separate rules.

**Dated evidence:**
- **19 September 2025, earliest verified public code:** [initial Rust commit `3f3f851`](https://github.com/Trac-Systems/ord-tap/commit/3f3f851a00301b780e333fc9d8a3c3eaf29920e3) and [intake gate source](https://github.com/Trac-Systems/ord-tap/blob/3f3f851a00301b780e333fc9d8a3c3eaf29920e3/src/index/updater/inscription_updater.rs#L984-L989) accept `ct.starts_with("application/json")` alongside `text/`. The [District body parser at the same commit](https://github.com/Trac-Systems/ord-tap/blob/3f3f851a00301b780e333fc9d8a3c3eaf29920e3/src/index/updater/inscription_updater/tap/ops/bitmap.rs#L13-L23) requires canonical `<height>.bitmap` text.
- **25 September 2025, verified retention:** [commit `acf6b7b`](https://github.com/Trac-Systems/ord-tap/commit/acf6b7bbc7862e50999edd42c02ae170dfe23eea) preserves the `application/json` string prefix while narrowing the text branch to `text/plain` and adding single-level effective-payload resolution. [Updated intake source](https://github.com/Trac-Systems/ord-tap/blob/acf6b7bbc7862e50999edd42c02ae170dfe23eea/src/index/updater/inscription_updater.rs).
- **Before 19 September 2025:** The original 2023 Trac writer's JSON MIME policy is not established by the public API README or by the later Rust implementation. This is an **earliest verified public snapshot**, not a demonstrated introduction date.

**Extracted candidate registry rule:** *JSON MIME Exception*, proposed default `0` (off). When enabled, allow the declared `application/json` content-type label for an otherwise canonical District claim; do **not** interpret arbitrary JSON-formatted bodies as claims.

**Registry status:** Already separately documented in [JSON MIME exception](../ruleset/District%20Rule%20Registry/json-mime-exception.md). **No registry edits or numbering made by this page.**

**Open checks:** Seek 2023 writer evidence for historical introduction. Test the independently registered [MIME prefix-compatibility option](../ruleset/District%20Rule%20Registry/mime-string-prefix-compatibility.md); do not fold MIME-prefix quirks into the JSON MIME-label exception.

### TRAC-D03 — Nested delegate exclusion

**Definition:** A normal one-level delegation is A → B, where inscription A declares B as its content delegate and B does **not** itself delegate. A **nested delegate** is A → B → C (or longer), where the directly referenced delegate B has its own delegate tag. This is not the same thing as Ordinals parent/child provenance.

**Content semantics prerequisite (do not merge with the nested veto):**
- **Own/undelegated content** means the bytes actually stored in inscription A's own reveal envelope. In Ord's Rust data model this is `Inscription.body()`, while `content_type()` reads A's own declared content-type field. [Ord source](https://github.com/ordinals/ord/blob/master/src/inscriptions/inscription.rs); [Ord recursive inscription info](https://github.com/ordinals/ord/blob/master/src/subcommand/server/r.rs).
- **Served/effective content** means the body returned for A by the ordinary `/content/A` endpoint. If A names B as a delegate, Ord substitutes B's **own body, content type and content encoding**. Ord's handler follows **one hop**, not an arbitrary A → B → C chain: [content handler](https://github.com/ordinals/ord/blob/master/src/subcommand/server/r.rs#L250-L279). The separate `/r/undelegated-content/A` route serves A's own body without following A's delegate: [handler](https://github.com/ordinals/ord/blob/master/src/subcommand/server/r.rs#L623-L645); [Ord documentation](https://docs.ordinals.com/inscriptions/recursion.html).
- These are distinct District eligibility questions: (1) are inscriptions carrying a delegate tag eligible, (2) is a claim's canonical body tested against A's stored bytes or the one-hop effective body, and (3) if delegates are allowed, is a second-hop delegate tag on B disqualifying? A nested-delegate exclusion only answers **(3)** and presupposes an answer to **(1)**; it must not silently dictate **(2)**.
- **Trac historical consequence:** In the 19–24 September 2025 public Rust snapshots, the Bitmap parser was passed the original `payload`; by [25 September 2025 `acf6b7b`](https://github.com/Trac-Systems/ord-tap/commit/acf6b7bbc7862e50999edd42c02ae170dfe23eea), the code resolves one-level delegate to `payload_eff` and passes *that* to MIME and District body checks. This is a separately significant change in what 'content' qualifies; audit it as its own candidate rule. The pre-801,993 fast path skipping the nested guard in earlier snapshots does **not** establish successful claims using delegated content there.

**Implementation behaviour and activation:**
- The Rust code tests whether the inscription referenced by A's delegate tag itself has a delegate, using `index.get_inscription_by_id(delegate_id)` followed by `insc.delegate().is_some()`. When that check is true, the inscription creation handler returns without registering the District. This is a specific **second-hop veto**, not an unconditional ban on all one-level delegates.
- In the **initial public Rust snapshot (19 September 2025)**, the Bitmap feature is gated at mainnet block **779,832** and the broader TAP processing at **801,993**. For heights **779,832–801,992**, the Bitmap creation path is executed **before** the nested-delegate veto, which means this particular test does **not** run on that path. At and after **801,993**, the test precedes the Bitmap creation call. **This does not by itself establish that a given nested claim was accepted in the earlier range**: content type, original-body parsing and other checks still matter.
- In the **25 September 2025** revision, the nested check was moved **ahead of the TAP-start split**, after the Bitmap activation check. It consequently runs for Bitmap processing from mainnet block **779,832** onward when the revised implementation replays history. The same revision also resolves the *effective payload* from a permitted single-level delegate before testing MIME and District body; that delegate-resolution behaviour should remain distinct from the nested-delegate veto.

**Extracted candidate District rule:** *Nested Delegate Exclusion*, binary **on/off**: when on, an inscription naming B as its delegate is ineligible if B itself names another delegate. This must not be conflated with (a) prohibiting all delegates or (b) resolving a one-level delegate's body. **Registry candidate default is provisionally `0` (off), not a settled Standard-content decision.** See [the unresolved District content question](../ruleset/District%20Rule%20Registry/DISTRICT-CONTENT-OPEN-QUESTION.md).
